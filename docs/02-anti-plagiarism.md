# 02 · 反抄袭与去行业化

> 本文档解释 ai-pm-hub 如何避免「方法论框架」被误用为「第三方素材的复制」。

## 这份文档要解决的问题

ai-pm-hub 的**方法论框架**完全来自作者原创沉淀。但**样例**（`_example-*.md`）来源于第三方培训/学习材料中方法论的应用方式——这带来两类风险：

1. **误用风险**：读者把方法论「复刻」到自己项目时，可能把样例里的占位符替换为真实产品名，导致第三方素材的实质性内容被二次传播
2. **合规问题**：任何残留的具体名称（产品 / 厂商 / 地区 / 学科）都可能引发版权或商标争议

所以**所有样例在沉淀时必须做去行业化处理**，且这个过程要**可审计**。

## 两条核心原则

### 原则 1：方法论骨架属于仓库，素材实质性内容属于第三方

| 学的是方法论（要开源） | 留下的是素材实质性内容（不公开） |
|----------------------|------------------------|
| 「状态机要包含失败与取消终态」 | 「某系统的 5 个具体失败态」 |
| 「多引擎降级要按精度切」 | 「某 OCR 用 Tesseract + PaddleOCR 兜底」 |
| 「假设的置信度要 4 级量表」 | 「某 AI 助手面临的 12 个具体假设」 |
| 「评测体系分层 L0–L6」 | 「某 LLM 在某类题上的具体通过率」 |

仓库沉淀的是**方法论骨架**。具体素材的实质性内容**不属于本仓库**。

### 原则 2：样例必须可替换

每份 `_example-*.md` 必须满足：

- **结构可复用**：状态机/矩阵/降级链的结构清晰可见，读者换场景时能直接照搬结构
- **内容可替换**：行业专属内容（人名、产品名、术语）一眼能识别为「需要替换的占位」
- **不需要二次创作**：读者不需要回去问「这个示例是什么」，换名字就能用

> 判别标准：把 `_example-*.md` 里所有 `[示例项目A]` / `[某学科]` 占位符替换为「[你的项目]」/「[你的学科]」，**文档结构与可执行细节不应出现任何不通顺**。

## 去行业化的 4 个步骤

### 步骤 1：识别「具体名称」

每份源素材都会混着「方法论骨架」与「具体名称」。先用「只读抽样」摸清每节主题，然后用以下清单识别「具体名称」：

- **具体产品/技术栈名**：Tesseract、PaddleOCR、讯飞、React、Vue、ChemAI 等
- **具体业务术语**：化学方程式、配平、氧化还原、选考等
- **具体地域/客户**：湖南、北京某高中、某教研员等
- **具体数字/数据**：通过率、参考人数、市场占比（这些是具体素材的内部数据，不应公开）
- **具体人员/机构**：校长姓名、合作伙伴、竞品名

### 步骤 2：泛化或替换

按以下优先顺序处理：

| 具体名称 | 替换为 |
|---------|------|
| 具体产品/技术栈 | 通用角色（如「文档解析引擎 A / B」）或中性占位 `[某厂商]` |
| 具体业务术语 | 通用类比（如「学科专属校验算法」） |
| 具体地域/客户 | `[某地区]` / `[该领域]` / `[核心客户群]` |
| 具体数字 | 「保留 N% 提升 / M 倍增长」+ 待具体场景填入 |
| 具体人员/机构 | 移除（不替换，因为不传递方法论价值） |

### 步骤 3：自检

用以下命令做去行业化质检：

```bash
# 反向检查：reference 文件中不应出现具体名称
# 命中数应为 0；命中要么删、要么用通用表述替换
grep -rE "具体产品名|具体地域|具体厂商" \
    skills/*/references/*.md 2>/dev/null
```

> ⚠️ **macOS 的 BSD `grep` 对中文 `|` 交替会静默漏检，必须用 `grep -E`**（这条已经被作者踩过 4 次坑）。

### 步骤 4：样例文件头声明

每个 `_example-*.md` 文件，**开头必须**有一行：

```markdown
> 本文件是「方法论的呈现示例」，不是「事实陈述」。样例为基于第三方培训素材的方法论重构，
> 已做去行业化处理；跨领域使用时只观察结构/状态机/矩阵/标注方式，行业细节一律按新场景重新生成。
```

这是合规意义上的「不构成抄袭主张」的声明。

## 4 种常见反模式

### 反模式 1：「素材实质性内容混入方法论」

❌ 错误：
> **化学 OCR 系统必须支持化学方程式配平识别**（因为某考试里配平题占 15%）

✅ 正确：
> **多模态识别类系统必须支持学科专属格式的子引擎**（与通用引擎并行，精度不达标时降级到人工）

### 反模式 2：「具体数字被当成方法论」

❌ 错误：
> **某 AI 助手的最佳团队规模是 3 算法 + 2 工程 + 1 教研**

✅ 正确：
> **小型 AI 产品团队的常见配置是 N 工程师 + M 算法 + 1 领域专家，N/M 根据项目复杂度调整**

### 反模式 3：「方法论被绕开」

❌ 错误：把「方法论」直接写为「工具选型建议」
> **AI 出题用 GPT-4 比用 Claude 好，因为……**

✅ 正确：方法论必须是**抽象判断框架**
> **AI 出题工作台选型的三个判断维度：① 长上下文稳定性 ② 工具调用准确度 ③ 成本可承受**（不指定具体模型）

### 反模式 4：「样例过长」

❌ 错误：`_example-*.md` 长达 1000+ 行
> 读者会被迫读完整个素材才能理解方法论

✅ 正确：`_example-*.md` 控制在 200 行以内
> 只摘 3–5 个最能体现方法论的**片段**（每段先写「示范点：…」再贴精简后的成品片段），结尾一节「把样例换成新场景的动作清单」

## 用户反馈与处理

如果有人认为本仓库内容涉嫌抄袭、侵权或第三方权利误用：

1. **不要公开评论**，先发 Issue 或邮件给作者
2. 作者承诺 24 小时内响应
3. 涉及侵权的文件会被立即删除或修改

## 总结：去行业化自检 10 条

提交 reference 之前，对照打勾：

- [ ] 文件中没有任何「具体产品名 / 技术栈名」当作方法论必选项
- [ ] 文件中没有任何「具体业务术语」需要读者查字典才能理解
- [ ] 文件中没有任何「具体地域 / 客户名」直接出现
- [ ] 文件中没有任何「具体数字」被当作通用结论
- [ ] 文件中没有任何「具体人员 / 机构名」被点名
- [ ] 替换所有具体名称后，文档结构与可执行细节完全通顺
- [ ] `grep -E "具体产品名|技术栈|地域"` 命中数为 0
- [ ] `_example-*.md` 开头有「本文件是方法论呈现示例，不是事实陈述」声明
- [ ] `_example-*.md` 总行数 ≤ 200
- [ ] 文件开头标注 `> 源文档：XX-XXX.md`（可回溯到源材料，但不暴露源材料具体内容）
