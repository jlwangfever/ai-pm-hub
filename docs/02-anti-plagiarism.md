# 02 · 反抄袭与去行业化

> 本文档解释 ai-pm-hub 如何避免「方法论框架」被误用为「行业知识抄袭」。

## 这份文档要解决的问题

ai-pm-hub 的方法论来自作者的真实产品项目 **ChemAI**（智辅化学）。如果直接分享，可能引发两类风险：

1. **抄袭嫌疑**：他人把方法论「复刻」到自己项目时，可能把化学教育的行业知识也复制走
2. **合规问题**：ChemAI 内部使用的数据、用户、商业计划等敏感信息可能意外泄露

所以**所有样例在沉淀时必须去行业化**，且这个过程要**可审计**。

## 两条核心原则

### 原则 1：方法论骨架属于仓库，行业知识属于项目

| 学的是方法论（要开源） | 留下的是行业知识（不公开） |
|----------------------|------------------------|
| 「状态机要包含失败与取消终态」 | 「化学批改系统具体的 5 个失败态」 |
| 「多引擎降级要按精度切」 | 「化学 OCR 用 Tesseract + PaddleOCR 兜底」 |
| 「假设的置信度要 4 级量表」 | 「化学 AI 助手面临的 12 个具体假设」 |
| 「评测体系分层 L0–L6」 | 「化学 LLM 在化学题上的具体通过率」 |

仓库沉淀的是**方法论骨架**。具体行业的具体应用留给**项目仓库**。

### 原则 2：样例必须可替换

每份 `_example-*.md` 必须满足：

- **结构可复用**：状态机/矩阵/降级链的结构清晰可见，读者换行业时能直接照搬结构
- **内容可替换**：行业专属内容（人名、产品名、术语）一眼能识别为「需要替换的占位」
- **不需要二次创作**：读者不需要回去问「这个 ChemAI 具体是什么」，换名字就能用

> 判别标准：把 `_example-*.md` 里所有「化学」字眼替换为「[你的行业]」，**文档结构与可执行细节不应出现任何不通顺**。

## 去行业化的 4 个步骤

### 步骤 1：识别「行业专属内容」

每份源材料都会混着两类内容。先做**只读抽样**（grep 标题骨架）摸清每节主题，然后用以下清单识别「行业专属」：

- **具体产品/技术栈名**：Tesseract、PaddleOCR、讯飞、React、Vue
- **具体业务术语**：化学方程式、配平、氧化还原、选考
- **具体地域/客户**：湖南、北京高中、化学教研员
- **具体数字/数据**：通过率、参考人数、市场占比（这些是 ChemAI 项目的内部数据，不应公开）
- **具体人员/机构**：校长姓名、合作伙伴、竞品名

### 步骤 2：泛化或替换

按以下优先顺序处理：

| 行业专属内容 | 替换为 |
|------------|------|
| 具体技术栈 | 通用角色（如「文档解析引擎 A / B」）或中性占位 |
| 具体业务术语 | 通用类比（如「学科专属校验算法」替代「化学方程式配平」） |
| 具体地域/客户 | 「该领域 / 该区域 / 核心客户群」 |
| 具体数字 | 「保留 N% 提升 / M 倍增长」+ 待具体场景填入 |
| 具体人员/机构 | 移除（不替换，因为不传递方法论价值） |

### 步骤 3：自检

用以下命令做去行业化质检：

```bash
# 反向检查：reference 文件中不应出现行业专属词
# 命中数应为 0；命中要么删、要么用通用表述替换
grep -rE "化学|高考|配平|氧化还原|湖南|讯飞|真题|错题" \
    skills/*/references/*.md 2>/dev/null
```

> ⚠️ **macOS 的 BSD `grep` 对中文 `|` 交替会静默漏检，必须用 `grep -E`**（这条已经被作者踩过 4 次坑）。

### 步骤 4：样例文件头声明

每个 `_example-*.md` 文件，**开头必须**有一行：

```markdown
> 本文件是示范参考，不是模板。样例沉淀自作者 ChemAI 真实项目，已去行业化处理；
> 跨领域使用时只观察结构/状态机/矩阵/标注方式，行业细节一律按新领域重新生成，绝不照搬。
```

这是法律意义上的「不构成抄袭主张」的声明。

## 4 种常见反模式

### 反模式 1：「行业知识混入方法论」

❌ 错误：
> **化学 OCR 系统必须支持化学方程式配平识别**（因为高考题里配平题占 15%）

✅ 正确：
> **多模态识别类系统必须支持学科专属格式的子引擎**（与通用引擎并行，精度不达标时降级到人工）

### 反模式 2：「具体数字被当成方法论」

❌ 错误：
> **化学 AI 助手的最优团队规模是 3 算法 + 2 工程 + 1 教研**

✅ 正确：
> **小型 AI 产品团队的常见配置是 N 工程师 + M 算法 + 1 领域专家，N/M 根据项目复杂度调整**

### 反模式 3：「方法论被绕开」

❌ 错误：把「方法论」直接写为「工具选型建议」
> **AI 出题用 GPT-4 比用 Claude 好，因为……**

✅ 正确：方法论必须是**抽象判断框架**
> **AI 出题工作台选型的三个判断维度：① 长上下文稳定性 ② 工具调用准确度 ③ 成本可承受**（不指定具体模型）

### 反模式 4：「样例过长」

❌ 错误：`_example-*.md` 长达 1000+ 行
> 读者会被迫读完整个 ChemAI 项目才能理解方法论

✅ 正确：`_example-*.md` 控制在 200 行以内
> 只摘 3–5 个最能体现方法论的**片段**（每段先写「示范点：…」再贴精简后的成品片段），结尾一节「把样例换成新领域的动作清单」

## 用户反馈与处理

如果有人认为本仓库内容涉嫌抄袭或侵权：

1. **不要公开评论**，先发 Issue 或邮件给作者
2. 作者承诺 24 小时内响应
3. 涉及侵权的文件会被立即删除或修改

## 总结：去行业化自检 10 条

提交 reference 之前，对照打勾：

- [ ] 文件中没有任何「具体产品名 / 技术栈名」当作方法论必选项
- [ ] 文件中没有任何「具体业务术语」需要读者查字典才能理解
- [ ] 文件中没有任何「具体地域 / 客户名」直接出现
- [ ] 文件中没有任何「具体数字」被当作通用结论
- [ ] 文件中没有任何「具体人员 / 机构名」被点名
- [ ] 替换所有行业词后，文档结构与可执行细节完全通顺
- [ ] `grep -E "化学|高考|配平|..."` 命中数为 0
- [ ] `_example-*.md` 开头有「本文件是示范参考，不是模板」声明
- [ ] `_example-*.md` 总行数 ≤ 200
- [ ] 文件开头标注 `> 源文档：XX-XXX.md`（可回溯到源材料，但不暴露源材料具体内容）
