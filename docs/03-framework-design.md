# 03 · 框架设计原则

> 本文档解释 ai-pm-hub 的 reference 框架在设计时遵循的核心原则。
> 新增 reference 时，对照打勾能保证整个仓库的方法论质量稳定。

## 5 个核心原则

### 1. 五段式结构（reference 的强制模板）

每份 `references/*.md` 必须按以下五段顺序写：

```
## 回答什么问题
## 怎么分析 / 怎么设计    （视文档类型选一个）
## 怎么写（文档结构） / 文档结构
## 及格线        （☑ 清单 4–6 条）
## 最易挂的坑    （2–4 条）
```

**为什么这五段**：
- 前三段是「内容」（回答问题、怎么做、写到哪算完）
- 后两段是「边界」（及格线是「必须满足」、最易挂的坑是「常见错误」）
- 读者读完前两段知道**该做什么**，读完中间段知道**做成什么样**，读完后两段知道**什么算交付**

### 2. 状态机、矩阵、降级链必须可执行

方法论要点必须写到**可执行细节**，不是泛泛而谈。

| 类型 | 「空话」 | 「可执行」 |
|------|--------|----------|
| 状态机 | 「要包含失败态」 | 「必须包含：loading / success / empty / error / unauthorized 5 态；每态给转移条件」 |
| 矩阵 | 「要画角色-资源-动作表」 | 「行列定义：行=角色（4 种），列=资源类型（6 类），单元格填「动作 + 限制」」 |
| 降级链 | 「多引擎要降级」 | 「主引擎置信度 < 0.6 降级到引擎 B；< 0.3 降级到人工；每级降级要记录到 audit log」 |
| 算法 | 「用规则 + 模型混合」 | 「规则先于 LLM：命中即返回；未命中再调 LLM；LLM 自检不能与 LLM 推理用同一模型」 |
| 评测 | 「分层评测」 | 「L0 单测 → L1 组件 → L2 端到端 → L3 人工判官 → L4 性能预算 → L5 回归；每层有门禁」 |

### 3. 跨领域通用，不绑定行业

每份 reference 必须满足：

- 换 3 个完全不同的领域（如教育→金融→医疗），结构与可执行细节都能直接套用
- 行业专属内容（人名、产品名、术语）一眼能识别为「需要替换的占位」

> 反模式与自检清单详见 [docs/02-anti-plagiarism.md](02-anti-plagiarism.md)。

### 4. 引用上游，不重新定义

设计文档（产品设计段位）有严格的**单向依赖原则**：

```
20 信息架构 → 21 交互流程 → 22 权限 → 23-28 业务系统
   → 29 Agent → 30 分析 → 31 评测 → 32 外围 → 33-37 技术基础
   → 38 前端规格 → 39 渲染 → 40 知识图谱 → 41 原型 → 42 架构 → 43 DESIGN.md
```

- 后面的文档**可引用**前面的决策（如 29 号引用 22 号的角色表）
- 后面的文档**不可重新定义**前面的决策
- 每份文档只写**该阶段能做的决策**

> 违反这个原则会导致文档互相矛盾、维护成本指数级上升。

### 5. 及格线必须可勾选，不能模糊

及格线 4–6 条，每条用 ☑ 符号开头，方便自检。

❌ **反例**（模糊）：
- 及格线：内容要完整 / 逻辑要清晰 / 表达要专业

✅ **正例**（可勾选）：
- ☑ 状态机枚举完整（含 loading/success/empty/error/unauthorized）
- ☑ 每个状态都有转移条件与超时上限
- ☑ API 端点给完整矩阵（含鉴权与限流）
- ☑ 数据隔离方案显式声明（多租户/角色/字段级 三选一）
- ☑ 「不在范围内」章节明确列出

## reference 的「写在文件里」与「不写在文件里」

### 写在文件里

- 方法论骨架（结构、状态、矩阵、降级链、流程）
- 通用方法论要点（如「不依赖同一模型自检」）
- 可执行细节（具体到字段名、状态值、API 路径格式）
- 「不在范围内」声明
- 反模式 / 最易挂的坑

### 不写在文件里

- 具体产品/技术栈的「推荐」或「反对」——会变成软文
- 具体行业的术语解释——读者换行业后失效
- 具体数字（团队规模、参数阈值）——这些是项目决策，不是方法论
- 工具对比、UI 截图——属于产品成果，不是方法论
- 商业评估（投资回报、市场份额）——属于具体业务

## 文档目录的 01-/02-/03- 顺序

仓库使用两位数编号 `01-/02-/03-` 顺序，而不是 L1/L2/L3 分类——因为：

- 流程图天然有先后顺序，编号 = 流程顺序
- 不存在「L1 vs L2 哪个先写」的歧义
- 跨子技能之间的衔接天然清晰

> 实际执行中曾考虑过 L1/L2/L3 顶层分类，被否决：分类会带来「哪个文档属于哪层」的人为判断。

## 命名规范

| 类型 | 命名 | 例子 |
|------|-----|------|
| reference 文档 | `XX-主题.md`，XX 为 2 位数字 | `02-swot.md` |
| 框架总览 | `framework-overview.md` | `market-insight-writer/references/framework-overview.md` |
| 示范样例 | `_example-描述.md` | `_example-chemai.md` |
| 教学课件 | `courseware-主题.md` / `.html` | `courseware-1to3.md` |
| 子技能主文件 | `SKILL.md`（大写） | `ai-pm-hub/SKILL.md` |

> 示范样例的 `_` 前缀用于在 `ls` 中排在最前，提示读者「先读这个」。

## 沉淀质量自检（5 步）

新增或修改 reference 时，按顺序检查：

1. **结构合规**：五段式完整、顺序正确、开头有 `> 源文档` 行
2. **去行业化**：`grep -E "化学|高考|..."` 命中数为 0
3. **可执行细节**：状态机/矩阵/降级链/算法/评测有具体数字、字段、阈值
4. **及格线可勾选**：4–6 条用 ☑ 开头，无模糊表述
5. **不孤立**：上游引用正确，不重新定义上游决策

## 与「五段式」相关的反模式

### 反模式 A：「长篇散文」

❌ 写 500 行连续段落，读者无法快速定位
✅ 多用表格、列表、状态机图、矩阵图

### 反模式 B：「什么都说」

❌ 及格线写 10+ 条，包括细节挑刺
✅ 及格线 4–6 条，覆盖「交付物形态」而非「细节完美度」

### 反模式 C：「没写什么是不做的」

❌ 写完「怎么做」就结束
✅ 明确「不在范围内」声明——告诉读者这个文档**不**回答什么问题

## 总结

一份好的 reference 应该让读者：

1. 5 分钟读完「回答什么问题」+「及格线」+「最易挂的坑」——知道**该做什么、不该做什么**
2. 30 分钟读完「怎么分析」+「怎么写」——知道**怎么落地**
3. 跨领域使用时**直接照搬结构**，替换行业内容即可
