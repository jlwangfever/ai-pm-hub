# AI 产品经理方法论中心（AI PM Hub）

AI 产品经理各类方法论的**统一入口**。它本身不重复任何具体方法论，只做三件事：**展示能力地图 → 识别意图路由 → 串联跨能力流程**。

## 核心理念

- **总入口，不是方法论本身**：具体怎么写市场洞察、怎么写 PRD，都在子 skill 里。本 skill 只负责「现在该用哪个能力」「一个完整的产品流程该怎么串」。
- **能力地图**：一眼看清 AI PM 方法论当前覆盖哪些能力、各自做什么。
- **可扩充**：新增能力只改 `references/capability-map.md` 的能力清单 + 本文件的「路由规则」，不动核心结构。
- **跨领域通用**：所有子 skill 学到的都是「方法论」而非「行业知识」——给教育、医疗、金融任何领域都能复用，绝不照搬样例的行业细节。

## 跨能力编排（产品全流程）

AI PM 从 0 到 1 的完整链路（八段流程，五个子技能承载）：

```
1 市场洞察 ─→ 2 用户与价值 ─→ 3 验证与商业 ─→ 4 产品设计 ─→ 5 PRD ─→ 6 DESIGN.md ─→ 7 原型设计 ─→ 8 UI 实现
 ✅ 已启用      ✅ 已启用         ✅ 已启用         ✅ 已启用     ✅ 已启用    ✅ 已启用       ✅ 已启用      ✅ 已启用
```

> 注：第 6 段 DESIGN.md（43 号）、第 7 段原型设计（41+44 号）、第 8 段 UI 实现（45 号）按流程独立编号——DESIGN.md 是「给 AI 执行」的视觉规范，原型设计是编码前「先画施工图再盖楼」的验证物，UI 实现是编码阶段「用现成组件别造轮子」的方法论；三者仍由 `product-design-writer` 承载。

**各段内部的顺序：**

- **1 市场洞察**（`market-insight-writer`）：`PESTLE(环境) → 市场规模(数字) → SWOT ⇄ 竞品(互相印证) → 产品愿景(收成一句)`
- **2 用户与价值定义**（`user-value-definer`）：`用户画像(角色与 JTBD) → 价值主张(价值量化) → ICP(优先购买单位) → 定位(沟通信息) → 滩头(第一块细分市场)`
- **3 验证与商业模式**（`validation-business-model`）三条线：`验证线 假设 → 机会树 → Pre-Mortem`；`商业线 精益画布 → 北极星 → GTM → 功能优先级`；`干系人地图贯穿`
- **4 产品设计**（`product-design-writer`）八层递进：`信息架构 → 流程与权限 → 业务系统 → Agent → 数据与分析 → 支撑系统 → 技术基础 → 前端整合与原型验证`
- **5 PRD**（`prd-style-learner`）两阶段：`先 learn（学习我的 PRD 风格档案）→ 再 write（按风格写新 PRD）`
- **6 DESIGN.md**（`product-design-writer` / 43 号）四段生成法：`提取设计参数 → 抽象组件模式 → 翻译约束规则 → 整体约束与缺口表`，放项目根目录供 AI 编码代理自动遵守
- **7 原型设计**（`product-design-writer` / 41+44 号）五步流「先画施工图，再盖楼」：`① 七维度方案 → ② Review 三关（业务完整吗·断头路 / 状态异常覆盖吗 / 能直接交给开发吗，缺一退回）→ ③ 原型生成（HTML 可交互，交 figma / 墨刀 / stitch）→ ④ 需求标注追溯码 → ⑤ 原型说明文档（44 号：七节模块格式 + 【待确认】制度，开发无需追问即可开工）`；七维度 = 页面目标 / 用户角色 / 信息架构 / 业务流程（正常+分支+替代）/ 状态规则（加载/空/错）/ 异常处理 / 验收标准写细写死
- **8 UI 实现**（`product-design-writer` / 45 号）Vibe Coding 五步法：`问框架（技术栈是人定的，不是 AI 猜的）→ 选组件库（自做自己挑 / 公司沿用团队的）→ 对组件名（效果映射到库里真实组件，不确定先反问）→ 写代码 → 要迭代（一次只改一件事）`；核心原则：组件库里有现成的，别让 AI 从零造轮子

**承接关系（后一段引用前一段的结论）：**

| 从 | 到 | 要承接什么 |
|----|----|-----------|
| 1 市场洞察 | 2 用户与价值定义 | 市场规模与竞品结论决定 ICP 与滩头的边界；宏观环境决定定位的合规底线 |
| 2 用户与价值定义 | 3 验证与商业模式 | 用户画像的痛点 → 待验证假设；价值主张 → 画布的价值主张与定价依据；ICP → 客户细分与渠道 |
| 3 验证与商业模式 | 4 产品设计 | 功能优先级排序决定设计层与系统的落地顺序；北极星指标决定分析/评测体系要埋什么 |
| 4 产品设计 | 5 PRD | PRD 的「功能详述」引用设计文档的模块与状态；PRD 的「背景/目标」承接市场洞察与产品愿景 |

> 实证：ChemAI 真实 PRD（v4.3，生产阶段）第 18 章把段 1-3 的产出（NSM 7 标准验证、ICP 9 维加权、滩头阵地、TAM/SAM/SOM、已杀死方案）内嵌为 PRD 章节，验证了「1→2→3→5」承接链路；该 PRD 同时是第 5 段风格档案的结构变体 C 样本。
| 5 PRD / 4 产品设计 | 6 DESIGN.md | 从 35 设计系统（色值/字体决策）+ 38 前端规格（组件与状态）压缩提炼，零发明 |
| 4 产品设计 + 5 PRD | 7 原型设计 | **文档不孤立**：七维度方案以设计文档（20 信息架构 / 22 角色 / 35 设计系统 / 38 页面规格 / 43 DESIGN.md）为「长什么样」的依据，以 PRD 需求编号为「验收什么」的依据；上游没定义的进缺口表，不猜不造 |
| 6 DESIGN.md + 7 原型设计 | 8 UI 实现 | DESIGN.md 给视觉约束（色值/字体/组件规则），原型给交互与状态基准；写代码时组件优先级 = 组件库现成 > 组件加定制 > 从零手写 |

**当用户要求「完整做一遍」时**：按 1→2→3→4→5→6→7→8 顺序推进，每段收口后再进下一段；跨段时把上一段的结论作为下一段的既定输入，不要重新推导。

## 扩充指南（未来加新能力时照做）

1. 先确认新能力是一个**独立可复用**的方法论（有自己的框架 + 触发词 + 产出物），做成独立的子 skill（参考 `market-insight-writer` / `prd-style-learner` 的结构）。
2. 在 `references/capability-map.md` 的能力清单里加一行，标注 `skill 名`、覆盖内容、触发词、状态。
3. 在本文件「能力地图」表里同步加一行。
4. 在本文件「路由规则」表里加对应意图 → 子 skill 的映射。
5. 如有新的流程顺序，更新「跨能力编排」链路。

**原则：本 skill 只维护「地图 + 路由 + 编排」，不吞并子 skill 的方法论细节**——否则会越滚越大、难以维护。子 skill 保持独立可单独调用，本 skill 负责把它们串起来。

## 注意事项

- 识别意图有歧义时（如用户只说「帮我做个产品分析」），先反问一句澄清：是要市场洞察、PRD、还是完整流程？不要猜。
- 路由到子 skill 后，把用户意图、已有素材、约束一并交给子 skill，避免上下文丢失。
- 本 skill 不写方法论内容；如果子 skill 尚未覆盖某个需求，明确说「该能力未纳入，可考虑扩充」，而不是硬套现有能力。
