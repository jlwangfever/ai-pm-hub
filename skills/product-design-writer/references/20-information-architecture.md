> 源文档：20-信息架构与导航设计.md

## 回答什么问题

产品有哪些页面、分几端、各端页面怎么组织、导航怎么走、组件从哪取数？把「信息结构」这一层固定下来，作为后续流程、权限、业务系统设计的地基。

核心产出：三端页面树、导航机制（SPA/MPA 决策）、组件-数据源绑定表、子角色菜单差异矩阵。

## 怎么设计（框架/步骤）

### 1. 先定三端角色架构总览

按端建表，每端明确：目标设备（桌面/移动）、页面数量、主页、功能页面清单、特色结构（Tab/浮动按钮/头部功能区）。信息密度由设备决定——桌面端承载高密度工作台，移动端只留核心路径。

### 2. 画完整页面树（mindmap）

以根为产品名，逐端展开页面→子区域→组件。页面树要穷尽所有页面与关键组件，作为后续所有文档的「页面清单真相源」。

### 3. 定导航机制

明确路由策略决策：高频交互模块用组件化 SPA（客户端路由切换、共享设计系统与状态）；轻量页面用原生跳转/MPA。若产品含 Agent 能力，只需在架构层声明「Agent 可驱动页面跳转」这一能力存在，具体协议交 Agent 设计文档定义（单向依赖）。

### 4. 子角色菜单差异矩阵

不同角色看到不同导航菜单。用矩阵列出每个页面对各子角色的可见性（✅/❌），并统计各角色「合计可见」数量。菜单过滤逻辑在渲染时执行，矩阵是前端与权限矩阵的交叉依据。

### 5. 组件-数据源绑定表

每个页面/组件登记「数据来源」，做到组件到数据源 1:1 可追溯（如「侧边栏会话列表 ← 会话列表 API + 本地缓存」）。禁止出现「这个数据从哪来不清楚」的组件。

### 6. 前端模块地图（可选）

按「共享基础设施 / 页面专用逻辑 / 跨端引擎」三层划分 JS 模块并标注依赖关系，便于工程落地。

### 7. 信息密度分层原则（设计观）

桌面端承载高密度工作台（多 Tab、密集数据面板、拖拽上传），移动端只保留核心路径与轻交互（Tab 切换、卡片列表、对话浮层）。页面树与导航机制应体现这种「按设备决定信息密度」的决策。

**示例页面树片段（教师端）**：
```
教师端
├─ AI Agent 对话主面板（对话区 + 侧边栏 + 快捷芯片 + 上下文栏）
├─ 考试工作台（Tab1 出题 / Tab2 题库 / Tab3 真题 / Tab4 考试）
├─ 班级学情面板（KPI 卡 + 错误率图 + 障碍饼图 + 趋势图）
├─ 学生管理（统计栏 + 搜索 + 卡片网格 + 详情抽屉）
├─ 障碍诊断（班级/考试选择 → 分布图 → 分组列表 → 计划面板）
├─ 答题卡识别 / 批改
```
每片叶子都要在「组件-数据源绑定表」里有对应行。

## 文档结构

1. **三端角色架构总览**：设备、页面数、主页、功能页、特色结构
2. **完整页面树**：mindmap 穷尽三端页面与组件
3. **导航机制**：路由策略（SPA/MPA 决策）、Agent 导航能力声明
4. **子角色菜单差异矩阵**：页面 × 角色可见性
5. **各页面组件清单与数据依赖**：分端表格，组件↔数据源绑定
6. **前端模块地图**（可选）：三层模块与依赖

## 及格线

- ☑ 三端页面树完整，穷尽所有页面与关键组件
- ☑ 导航机制明确给出 SPA/MPA 路由决策及理由
- ☑ 每个组件都有可追溯的数据来源（组件-数据源绑定）
- ☑ 子角色菜单差异有矩阵（页面 × 角色 ✅/❌ + 合计可见数）
- ☑ 声明了与后续文档的依赖边界（权限矩阵、Agent 协议不在本文定义）

## 最易挂的坑

- **只列页面不画树**：没有 mindmap 式的完整页面树，后续流程/权限文档找不到「页面真相源」，容易漏页面或重复定义。
- **组件不绑定数据源**：写了组件却没写它从哪个 API/本地缓存取数，落到工程层会变成「不知道调什么接口」，等于没设计。
- **菜单差异无矩阵**：子角色可见性用文字描述而非矩阵，前后端对「谁看得见什么」理解不一致。
