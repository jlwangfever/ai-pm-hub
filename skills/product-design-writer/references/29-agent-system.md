> 源文档：29-Agent对话系统设计.md

## 回答什么问题

Agent 系统把用户的自然语言（教师指令 / 学生提问 / 家长查询）转化为可执行的工具调用链，并流式推送过程与结果。它不是「一个超长 Prompt」，而是一组**职责单一、分层协作**的子系统：意图路由、角色隔离、护栏、规划、上下文与记忆、工具注册、审计、错误回退、流式协议、模型供给。

核心产出：单/多智能体架构选型 + 工具注册表 + Persona 隔离 + 四层护栏 + 意图分类 + 规划/记忆/审计/回退。

## 怎么设计（框架/步骤）

**1. 架构选型：单 Agent ReAct + Persona 过滤（优于多 Agent 路由）**
- 多智能体（Coordinator→Router→SubAgent）路由准确率约 70%，协调开销大；单 Agent 全量注入工具 + 按角色过滤，路由准确率提到 85%+，LLM 调用次数减半。
- 决策证据：对比表（路由方式/准确率/调用次数/状态复杂度/维护性）。

**2. 工具注册表（编译时闭合）**
- 每个工具在元数据表登记：可用 persona 列表 + 每轮最大调用次数 call_limit（按重要性/破坏性分严格1次/中等2次/宽松3次/开放5次）。
- 启动阶段做完整性断言：每个注册工具都有元数据、每条元数据对应已注册工具，**任何遗漏在启动即暴露**。

**3. Persona 系统（角色隔离）**
- 每个角色用 YAML 定义：system_prompt + available_skills 白名单 + data_access（可见/不可见数据项）。
- 工具集 = 元数据注册集 ∩ 配置白名单，**交集为空则不注入**，杜绝越权。

**4. Guard 护栏层（四层，每层返回结构化错误，由 LLM 决定如何继续）**

| 层 | 检查 | 拦截后动作 |
|----|------|-----------|
| 1 前置 | 必填参数 | LLM 向用户追问补全 |
| 2 限流 | 超 call_limit | 基于已有结果继续 |
| 3 去重 | 同 tool+args 重复 | 跳过，防循环 |
| 4 审批 | 破坏性操作未审批 | 暂停→确认→恢复 |

**5. Gateway 意图分类（LLM 优先 + 关键词兜底）**
- 主路径轻量 LLM 判 intent；失败降级 ~16 组关键词。`navigate` 类走快捷路径，跳过 ReAct 直接推页面跳转。
- 不确定时一律走 chat。

**6. Planner（目标拆解）**：拆为 ≤6 步、支持依赖注入（变量引用前序输出）、失败时 fallback 单步（关键词匹配）。

**7. 上下文与记忆（防 token 爆炸）**
- 三层裁剪：无条件保留最近 6 条 + 关键词命中保留 + ≥10 条丢弃则 LLM 摘要（失败降级纯裁剪）。
- 三层记忆：工作（滑动窗口）/ 情景（本次对话事件）/ 档案（跨请求持久，以 System Message 注入）。

**8. 审计 + 错误回退 + 协议 + 供给**
- 审计：JSONL、敏感字段脱敏、环形缓冲、**绝不阻塞主流程**（try-except 静默）。
- 错误体系：每个异常带 code + recoverable，可转 SSE error 事件；递归耗尽给友好提示。
- SSE 事件协议：phase/tool_call/tool_result/text/component/navigate/error/done 等结构化事件。
- 多 Provider 三级回退 + 指数退避（最多 3 次）；Agent 工具 vs MCP 工具分工（LLM 自选 vs 外部系统集成）。

**9. 审批流的可恢复性**
- 审批请求持久化，确认/取消通过确定性重放恢复执行，避免 LLM 在审批点重新决策。
- 服务端身份注入：角色由服务端注入工具上下文，工具不信任 LLM 自报身份。
- 文件/命令类工具越出工作区时按次审批，单次放行不累积权限。

## 文档结构

1. **系统定位**：能力闭环、与前端关系、设计目标、核心指标、不在范围内
2. **架构演进**：v1 多智能体问题 → v2 单智能体对比表 → 共存策略
3. **工具目录**：元数据注册、按领域分组的工具表（含限次/角色）
4. **Persona / Guard / Gateway / Planner / 上下文 / 记忆 / 审计 / 错误处理**
5. **MCP / SSE 协议 / Provider 回退 / 依赖注入 / 模型工厂 / Skills 注册**

## 及格线

- ☑ 架构选型有对比证据（单 vs 多智能体的准确率/开销权衡）
- ☑ 工具有注册表且启动期完整性断言，call_limit 分级
- ☑ 角色隔离用「元数据∩白名单」交集，且 data_access 定义可见边界
- ☑ Guard 四层职责单一、各自有明确拦截动作与可恢复性
- ☑ 有意图分类兜底、上下文裁剪、审计脱敏不阻塞、Provider 回退

## 最易挂的坑

- **多智能体路由即用**：路由准确率掉到 70% 且协调开销翻倍，优先验证单 Agent + 角色过滤是否够用。
- **护栏只做审批**：缺前置/限流/去重三层，LLM 易陷入工具调用死循环或越权。
- **记忆全量进上下文**：不裁剪导致 token 爆炸、成本失控，必须三层裁剪 + 摘要降级。
