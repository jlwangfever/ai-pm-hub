# 33-37 技术基础层设计框架（合并）

> 源文档：33-数据模型设计.md / 34-API设计.md / 35-设计系统.md / 36-桌面应用与打包设计.md / 37-技术选型与工具链.md

本文档是「产品设计」阶段技术基础层（数据模型 / API / 设计系统 / 桌面与部署 / 技术选型）的合并写作框架。五份文档共用一个目标：把信息架构与交互设计**落到可被工程实现的规格**，而不是停留在原型图。写这类文档时，先讲「长什么样」（结构骨架），再给「字段级 / 参数级 / 色值级」的精确约定，最后用「隔离 / 兼容 / 复用」三件事收口。

## 数据模型（对应 33）

回答：系统里有哪些东西、它们之间怎么关联、多租户数据怎么隔离。

**写法要点**：

1. **先画 ER 总览**：用实体关系图一次性回答「有哪些实体 + 它们如何关联」。去掉关系线看实体清单，加上关系线看业务链路。
2. **提炼核心数据链（3-4 条）**：用「组织链（容器→子容器→末端对象）/ 业务链（一次核心操作牵动的对象）/ 身份链（账户与角色）/ 家校或协作链」把 ER 图收敛成可被理解的叙事，方便评审者秒懂数据流向。
3. **逐实体给字段规格**：每个核心实体给「字段名 / 类型 / 约束 / 说明 / 示例值」表，不要只列类名。重点实体（如学生画像、作答记录）要写出驱动业务算法的关键字段（如连续正确/错误计数器、障碍占比 JSON）。
4. **枚举类型集中定义**：把所有用枚举约束取值范围的概念（状态、类型、难度、审核结果）收进一张表，统一取值与业务含义，避免散落。
5. **关键结构化数据单独说明**：以 JSON 存储的复合业务数据（画像、统计、审核报告、计划）给出字段含义，说明何时异步更新。
6. **数据隔离方案必须写**：明确多租户边界——以哪一层（组织/班级/账户）为隔离核心，教师、家长、学生各自可见范围，匿名化聚合数据的呈现规则。

**示例——核心业务实体字段规格表（节选）**：

| 字段 | 类型 | 约束 | 说明 | 示例值 |
|------|------|------|------|--------|
| student_id | String | UNIQUE, NOT NULL | 学生唯一标识 | "stu_001" |
| barrier_profile | JSON | — | 障碍类型占比（三值和为 1） | {concept:0.3, read:0.5, expr:0.2} |
| consecutive_wrong | Int | DEFAULT 0 | 连续答错计数（阈值判断用） | 3 |
| bind_code | String(6) | — | 家长绑定码 | "A1B2C3" |

**示例——枚举类型定义表**：

| 概念 | 可选值 | 说明 |
|------|--------|------|
| 题目难度 | 简单/中等/困难/竞赛 | 竞赛级不自动分配，仅手动 |
| 审核状态 | 通过/警告可用/阻断不可用 | 阻断的题目不下发 |

**及格线**：☑ 有 ER 总览 + 核心数据链叙事；☑ 核心实体有字段级规格；☑ 枚举类型集中定义；☑ 多租户/数据隔离方案明确。

## API 设计（对应 34）

回答：前后端怎么对话——端点怎么组织、流式输出怎么传、认证授权怎么收口。

**写法要点**：

1. **端点全景矩阵**：按业务域分组（认证/组织/核心业务/报告/通知/AI Agent/集成），每组给 `Router 前缀 + 核心端点 + 所在模块`。让读者一眼看到「有多少个域、每个域有哪些能力」。
2. **关键 API 详述**：挑 5-10 个核心接口，给「请求体字段（名/类型/示例）+ 成功响应字段 + 错误响应」。流式接口单独说明响应是事件流。
3. **SSE 事件协议**（若产品含流式 AI 输出）：用一张表枚举 `event` 类型与 `data` payload，并说明事件**顺序**（如 thinking → tool_call → token → done）。这是前端渲染层的契约，必须完整。
4. **认证体系**：JWT 签发/刷新流程 + 角色权限矩阵（域 × 角色，标注 R/W/-）。权限从「白名单 + 角色字段」双控。
5. **通用查询约定**：分页（limit/offset）、排序（sort_by/order）、筛选（keyword/status/日期区间）定义一套统一参数，所有列表接口复用。
6. **统一错误码体系**：给出分类规则——`error_code`（语义分类）+ HTTP 状态码 + `detail`（人话）+ `suggestion`（修复建议）。错误码按「校验/认证/权限/资源/业务规则/依赖不可用」分类，不要散在各处。
7. **速率限制**：默认全局限流（IP/分钟）+ 关键端点差异化限制 + 429 响应格式（含 Retry-After）。

**示例——SSE 事件协议表（节选）**：

| event | data payload | 说明 |
|-------|-------------|------|
| phase | phase 值（thinking/reply/awaiting_approval） | Agent 状态切换 |
| tool_call | name + args | 工具调用开始 |
| text | content | 流式文本输出 |
| component | component + params | 内联面板渲染指令 |
| done | thread_id + tool_calls 汇总 | 对话结束 |

事件顺序：`phase(thinking)` → `tool_call` → `text(多帧)` → `done`。

**示例——统一错误码分类规则**：

| 错误码 | HTTP | 类别 |
|--------|------|------|
| VALIDATION_ERROR | 422 | 请求体校验失败 |
| AUTHENTICATION_REQUIRED | 401 | 未认证 |
| PERMISSION_DENIED | 403 | 越权 |
| RESOURCE_NOT_FOUND | 404 | 资源不存在 |
| BUSINESS_RULE_VIOLATION | 400 | 业务规则冲突 |
| INTERNAL_ERROR | 500 | 服务内部错误 |
| LLM_SERVICE_UNAVAILABLE | 503 | 依赖不可用 |

**及格线**：☑ 有按业务域分组的端点矩阵；☑ 关键接口有请求/响应字段；☑ 有 SSE 事件类型与顺序（若含流式）；☑ 有角色权限矩阵；☑ 有统一错误码分类规则；☑ 有分页/筛选通用约定。

## 设计系统（对应 35）

回答：产品视觉气质是什么、怎么从理念落到色值/字体/组件/响应式。

**写法要点**：

0. **品牌决策用「提案制」，不让 AI 拍板**：色值是品牌决策，必须 AI 出 **2-3 套完整方案并列**（每套含：主色=系统声音 + 强调色=AI/特色声音 + 背景/表面层次 + 语义色通过/警告/阻断的浅底深字），每套附**论证链**（每个颜色为什么这么选、防止什么误用）、**自检**（语义色与主色是否冲突）与**方案对比表**（气质/适配场景/风险）。人选定后再细化成完整色板。多方案权衡能逼出单方案看不到的冲突（实测案例：某套墨绿主色方案在并列对比时才暴露与「通过绿」语义色的冲突）。
1. **设计理念与主题**：用一个核心隐喻定位产品气质（如「X 是学习的催化剂」），拆 2-3 根支柱，每根支柱对应一组具体设计决策。原则要可辩护，不能只说「现代好看」。
2. **技术实现方式**：说明设计令牌（design token）如何统一——颜色/字体/间距通过集中定义的类名或主题变量控制，保证跨页面一致。
3. **色彩系统分三层**：主色（定义产品气质，如品牌色/AI 色/背景色，各司其职）、语义色（通过/警告/阻断，用「浅底深字标签」降低噪音）、辅助色（边框/分区，不参与语义）。每层写明色值与用途边界，不混用。
4. **字体系统**：按用途分——标题（无衬线加粗）、正文（系统字体栈，无加载依赖）、等宽（专业符号/代码/数据对齐）。说明为什么专业内容需要等宽字体。
5. **专业符号渲染**：若产品涉及学科专属符号（公式、上下标、特殊记号），说明两条路径——后端返回前格式化 + 前端用渲染引擎（如 KaTeX 类）渲染；给输入语法→渲染效果对照表。
6. **组件设计**：对核心组件（按钮/卡片/标签/弹窗/输入框/状态占位）给变体表（视觉特征 + 使用场景），说明圆角/悬停/按压等交互细节。状态占位要覆盖空态/加载态/错误态的设计意图。
7. **响应式策略**：按使用场景（桌面/平板/手机）给布局策略表，区分数据密集端与移动优先端的「设计语言差异」。

**示例——色彩三层结构**：

| 层 | 变量 | 色值 | 用途边界 |
|----|------|------|---------|
| 主色 | 品牌色 | #002147 | 导航/按钮/标题（系统的声音） |
| 主色 | AI 色 | #0d7377 | AI 对话气泡/智能建议（AI 的声音） |
| 语义色 | 通过/警告/阻断 | 浅底深字 | 状态传达，不喧宾夺主 |
| 辅助色 | 边框/分区 | #e2e8f0 | 结构辅助，不参与语义 |

**示例——组件变体表（按钮）**：

| 变体 | 视觉特征 | 场景 |
|------|---------|------|
| 主按钮 | 品牌色实心白字 | 提交/生成/保存 |
| AI 按钮 | AI 色实心白字 | 智能类操作 |
| 次按钮 | 品牌色描边 | 取消/返回 |

**及格线**：☑ 有理念与主题且可辩护；☑ 色彩分主色/语义色/辅助色三层并带色值；☑ 字体按用途区分；☑ 核心组件有变体说明；☑ 有响应式分场景策略；☑ 品牌类决策（色板）走提案制——多方案 + 论证链 + 对比表，不直接定稿。

## 桌面与部署（对应 36）

回答：若产品要打包成桌面端，入口架构、打包流水线、与 Web 端差异、代码怎么复用。

**写法要点**：

1. **多入口架构**：若同一套前端要出多个端（如教师/学生/家长），用表格定义每入口的窗口尺寸、最小尺寸、加载 URL、目标用户。窗口尺寸本身是一种产品设计决策（移动端视口模拟）。
2. **内嵌服务器**：说明本地自包含方案（如内嵌 Web 框架 + 本地端口），关键决策表：服务器地址（仅本地更安全）、线程模型（daemon 自动终止）、日志级别、数据库（本地文件零运维）。
3. **启动就绪等待**：写清「启动服务 → 轮询探测端口 → 端口就绪再创建窗口」的序列，含最大等待时长与超时处理。
4. **打包流水线**：单文件打包模式、需显式声明的动态依赖（hidden-import）、输出结构（体积、重命名）。
5. **容器化替代方案**：给出 Dockerfile 关键步骤（基础镜像/依赖/端口/健康检查/启动命令）与 compose 编排（服务、数据卷持久化、env、restart 策略、按需 profile）。
6. **CI/CD**：并行 Job 表（确定性评测/导入检查/边界回归/构建），门禁策略（push 跑哪些、PR 额外跑哪些、发布前全量）。
7. **桌面 vs Web 差异**：一张对比表（运行环境/CORS/文件系统/窗口/存储/更新/离线），点明桌面端可直访本地文件、无 CORS、可离线。
8. **代码复用策略**：明确前端（仅窗口 URL 不同）+ 后端（完全共用）的复用边界，数据库文件共用规则。

**及格线**：☑ 多入口有尺寸/URL/用户表；☑ 内嵌服务器关键决策明确；☑ 有打包流水线要点；☑ 桌面 vs Web 差异对比；☑ 代码复用边界清晰。

## 技术选型（对应 37）

回答：每项关键技术「候选有哪些、按什么维度评判、为什么选这个、放弃了什么」。

**写法要点**：

1. **选型方法论三条**：够用就好不为未来过度设计；优先社区验证方案避免自研陷阱；每个选择记录为 ADR（架构决策记录：选了什么 + 为什么 + 放弃了什么）。
2. **给「候选 → 评判维度 → 决策理由 → 被否决原因」**：不要只写结论。例如模型服务选型用自研基准实测（设计覆盖核心场景的题集，逐家评分 准确率/可用率/延迟/成本/特有能力的维度）；Agent 框架选型给迭代历程与路由准确率对比；前端选型对比组件化 SPA 与手写 DOM 的成本收益。
3. **分领域选型表**：LLM Provider / Agent 框架 / 前端 / 数据库 / 识别解析管道 / Web 框架与 ORM / 向量库 / 调度 / 容器 / 打包 / 测试 / CI 各给「选择 + 核心理由 + 放弃方案」。
4. **降级与兜底链**：识别解析等多引擎场景写清降级顺序（主引擎失败 → 降级引擎 → 最终兜底），并说明路由策略。
5. **开发工具链**：说明工程实践分层（规格驱动 / TDD / 评测 Evals / Git），特别是评测的层级、门禁阈值与回归基线。

**示例——模型服务选型对比维度表**：

| 维度 | A | B | C |
|------|:--:|:--:|:--:|
| 领域准确率 | 20/20 | 20/20 | 18/20 |
| API 可用率 | 99.7% | 98.2% | 99.9% |
| 平均延迟 | 2.1s | 3.5s | 1.8s |
| 成本等级 | 最低 | 中 | 低 |
| 特有能力的 | 否 | 视觉+联网 | 否 |

决策：首选 C（延迟最低、可用率最高、配套视觉模型），A 作批量/回退，B 作需视觉/联网的兜底；放弃海外模型（合规/成本）与自部署（ROI 不匹配）。

**示例——ADR 记录格式**：

| ID | 决策 | 选择 | 放弃 | 原因 |
|----|------|------|------|------|
| ADR-1 | Agent 架构 | 单 Agent ReAct | 多 Agent 协作 | 路由准确率 87% vs 75%，延迟低 40% |

**及格线**：☑ 有选型方法论且记录 ADR 意识；☑ 关键选型给出候选对比与评分维度；☑ 每个重大决策有「放弃的方案 + 原因」；☑ 多引擎场景有降级链。
