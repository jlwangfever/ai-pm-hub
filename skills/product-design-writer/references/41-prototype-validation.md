# 41 原型验证写作框架

## 回答什么问题

设计文档与 PRD 都定稿之后，如何在**编码之前**用可交互原型把设计「试跑」一遍？本文档定义原型设计的四步流（**先画施工图，再盖楼**）、七维度方案骨架、Review 三关与需求标注追溯码，让原型从「看起来不错的 Demo」变成「可追溯、可验证的交付物」。

> **文档不孤立**：原型设计方案不是从零写的，它以两份上游文档为依据——**设计文档**（信息架构 20 / 页面规格 38 / 设计系统 35 / DESIGN.md 43）提供「长什么样、有哪些组件与状态」，**PRD** 提供「对应哪条需求、验收标准是什么」。写方案前先声明引用了哪些上游文档；上游没定义的写 `null` 并编入缺口表，不猜不造。

## 怎么设计（框架/步骤）

**前置检查**（进入前必过）：设计文档已读（能说出各页面名、组件表、色值字体）、PRD 已读（能定位每条需求编号）、DESIGN.md 已读（若有）、原型工具可用（figma / 墨刀 / stitch / AI 生成链路均可）。

**四步流**（方案层，每页循环执行）：

1. **① 方案设计（七维度）**：结合设计文档地址 + PRD，从七个维度写原型设计方案：
   | # | 维度 | 要求 |
   |---|------|------|
   | 1 | 页面目标 | 一句话说清该页帮用户完成什么 |
   | 2 | 用户角色 | 来自 22 权限模型的角色表，写明哪类角色可见 |
   | 3 | 信息架构 | 来自 20，写明页面在导航树的位置与入口 |
   | 4 | 业务流程 | 正常 + 分支 + 替代三条路径，缺一不可 |
   | 5 | 状态规则 | 加载 / 空 / 错三态全覆盖 |
   | 6 | 异常处理 | 超时、断网、权限不足、并发冲突等 |
   | 7 | 验收标准 | **写细写死**——「输错 3 次锁定 30 分钟并显示剩余时间」，不是「能正常登录」 |
   先出**计划方案**（页面清单 + 每页七维度的骨架）给干系人确认，再展开完整方案。
2. **② 方案 Review（三关，缺一退回）**：对照计划方案审一遍——
   - **业务完整吗**：有没有断头路（流程走到一半没有出口、按钮点了没去向）？
   - **状态异常覆盖吗**：每页三态与异常分支是否都设计了？
   - **能直接交给开发吗**：字段、状态、交互是否落到可编码颗粒度？
   三关全过才进入生成；任何一关不过，退回 ① 修方案。
3. **③ 原型生成（HTML 可交互）**：把方案翻译为原型工具可执行的提示词。提示词 = 组件清单（来自 38）+ 设计约束（色值写 `#002147` 不写颜色名、布局写 flex 结构、尺寸写具体 px、交互写触发方式与效果）+ 布局描述。一次描述 6-8 个核心组件最佳，复杂页（多 Tab）分多次生成再拼合。
4. **④ 需求标注（追溯码，分水岭）**：给原型设计方案做标注，**每条标注回答三个问题**——「对应哪条需求（PRD 编号）/ 体现在哪个元素（页面组件）/ 怎么验证（验收动作）」。做完这步，原型才从 Demo 变成交付物。

**三层对得上，才是好产品**：设计文档（图纸）→ 原型（沙盘）→ 代码（楼）。每页设计的落点都能对应到代码，验收时按「需求编号 → 原型元素 → 代码模块」追溯。

**逐页面对照验证清单**（生成后逐项打勾）：组件是否齐全、状态变体是否覆盖、颜色/圆角是否相符、交互是否生效。缺失项修改提示词重新生成；记录提示词与结果便于复现。

**常见错配与修复表**（必须沉淀）：

| 问题 | 原因 | 解决 |
|------|------|------|
| 两栏变上下堆叠 | 工具未理解布局 | 补 flex: 0 0 232px + flex:1 |
| 颜色跑偏 | 写名称不写色值 | 改写 `#002147` |
| 多 Tab 内容全显示 | 未实现 JS 切换 | 补显隐 div + 激活下划线 |
| 图表空白 | 引了外部库未加载 | 改纯 CSS/div 模拟 |

**提示词三连模板**（可直接复用，占位符按项目替换）：

1. `结合我的设计文档：<设计文档地址>，和我的 PRD：<PRD 地址>，从这七个维度给我写原型设计方案：页面目标 / 用户角色 / 信息架构 / 业务流程（正常+分支+替代）/ 状态规则（加载/空/错）/ 异常处理 / 验收标准写细写死——"输错 3 次锁定 30 分钟并显示剩余时间"，不是"能正常登录"。上来别直接写文档内容，先给我计划方案。`
2. `结合内容再审查一遍计划方案，没有问题之后写成完整的方案。要求：业务完整吗（断头路）？状态异常覆盖吗？能直接交给开发吗？`
3. `接下来给原型设计方案做标注，要求：每条标注回答"对应哪条需求 / 体现在哪个元素 / 怎么验证"——原型从"看起来不错的 Demo"变成"可追溯、可验证的交付物"。`

**工具交接**：原型设计方案完成后，直接交给 figma / 墨刀 / stitch 等原型工具执行生成；工具中性——示例以某一种链路为例，方法论不依赖具体工具。

**下游交接**：原型确认后，进入第 ⑤ 步——把原型翻译成开发可直接开工的《原型说明文档》（七节模块格式 + 【待确认】制度），见 `44-prototype-spec.md`。

## 文档结构

1. 本阶段目标 + 输入依据声明（引用了哪些设计文档与 PRD 章节）+ 前置检查表
2. 四步流定义（七维度方案 → 三关 Review → 原型生成 → 需求标注追溯码）
3. 提示词写法（要素提取 + 关键技巧 + 错配修复表）+ 提示词三连模板
4. 逐页面 Step（每页：方案 → Review → 生成 → 标注 → 对照验证清单）
5. 完成标准 + 产出文件清单（方案文档 + 原型文件 + 追溯标注表）

## 及格线

- ☑ 声明了输入依据（设计文档 + PRD 的具体章节/编号），上游没定义的进缺口表而非现场编造
- ☑ 每页方案七维度齐全，验收标准写细写死（有数字、有动作、有时长，无「能正常使用」式空话）
- ☑ 过了 Review 三关（无断头路、三态与异常全覆盖、达到可开发颗粒度）才进入生成
- ☑ 每条需求标注含三问答案（对应需求编号 / 体现元素 / 验证方式），可双向追溯
- ☑ 提示词含「色值/布局/尺寸/交互」四要素，有错配修复表
- ☑ 有完成标准（页面数 + 归档位置 + 标注表）

## 最易挂的坑

- **跳过方案直接生成**：上来就让工具画页面，七维度没人把关，断头路和缺失三态全留到开发阶段才爆。
- **验收标准写成空话**：「能正常登录」「体验流畅」不可验收；必须写死到「输错 3 次锁定 30 分钟并显示剩余时间」的颗粒度。
- **不做需求标注**：原型看着不错就归档，无法回答「这个按钮对应 PRD 哪条」——Demo 与交付物的分水岭就在第 ④ 步。
- **提示词写颜色名不写色值**：工具不识别「Oxford Blue」，只认 `#002147`，结果配色跑偏且难排查。
