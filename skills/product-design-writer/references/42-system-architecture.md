# 42 系统架构图文档写作框架

## 回答什么问题

当产品进入实现规划，如何用一组架构图把「整体怎么分层、核心推理/业务内部怎么运转、一次完整业务闭环数据怎么流、核心数据模型是什么、关键决策为何如此」讲清楚？本文档定义架构图类文档的写法——它既要给人看明白，也要作为后续开发的事实基线。

## 怎么设计（框架/步骤）

按「全景 → 核心机制 → 数据流 → 数据模型 → 决策记录」五段组织，每段用图（Mermaid/示意）为主、文字注解为辅。

**1. 系统分层架构**

用一张分层图呈现整体（如基础设施层 / 数据层 / 服务层 / 安全审核层 / 编排层 / 应用层），说明每层「依赖下层接口、向上暴露能力」，前端各端统一通过 API 网关访问。每层的职责一句话点明，突出与传统 CRUD 应用不同的核心层（如 Agent 编排层）。

**2. 推理/核心内部机制**

聚焦系统最具差异化的内部循环（如 Agent 的 ReAct 思考-行动-观察循环），画处理路径图，并给「关键设计决策表」：

| 机制 | 设计决策 | 说明 |
|------|---------|------|
| 递归/迭代上限 | 如 12 轮 | 单智能体足够覆盖完整链路 |
| 工具可见性 | Persona 白名单过滤 | 从源头杜绝越权 |
| 审批中断 | 框架原生中断 + 授权工具 | 状态随检查点持久化 |
| 去重保护 | 签名去重 + 相似度阈值 | 防重复调用与复述 |
| 状态持久化 | 每步检查点 | 中断可恢复 |

**3. 端到端数据流**

用时序图展现一次完整业务闭环（如「教师操作 → 学生接收 → 家长获取」）跨组件的数据流转，按阶段（rect 分区）标注，覆盖三端全部交互与跨层调用。

**4. 核心数据模型**

用 ER 图聚焦与核心闭环直接相关的实体及关系，红线标注关键关联。引用数据模型文档（另一份）做字段级细节，本文只讲结构与关联。

**5. 架构关键决策记录（ADR 表）**

全文档最重要的收口。一张表列出每条关键决策：`ID / 决策项 / 选择 / 放弃的方案 / 原因`。例如 Agent 架构（单 vs 多）、前端架构（组件化 SPA vs 手写）、数据库（SQLite vs PostgreSQL）、流式协议（SSE vs WebSocket）、长期记忆方案等。每条 ADR 都要写「为什么放弃替代方案」——这是架构文档的价值所在。

**示例——关键设计决策表（核心机制节）**：

| 机制 | 设计决策 | 说明 |
|------|---------|------|
| 迭代上限 | 12 轮 | 单智能体足够覆盖完整链路 |
| 工具可见性 | Persona 白名单 | 从源头杜绝越权 |
| 审批中断 | 框架原生中断 + 授权工具 | 状态随检查点持久化 |
| 去重保护 | 签名 + 相似度 >0.7 | 防重复调用与复述 |
| 状态持久化 | 每步检查点 | 中断可恢复 |

**示例——ADR 记录表（节选）**：

| ID | 决策 | 选择 | 放弃 | 原因 |
|----|------|------|------|------|
| ADR-1 | Agent 架构 | 单 Agent ReAct | 多 Agent 协作 | 路由准确率 87% vs 75%，延迟低 40% |
| ADR-5 | 数据库 | 本地文件库 | PostgreSQL | 零运维，单容器部署，ORM 预留切换 |
| ADR-8 | 流式协议 | SSE | WebSocket | 单向推送更简单，浏览器原生支持 |

## 文档结构

1. 系统分层架构（图 + 分层职责）
2. 核心内部机制（图 + 关键设计决策表）
3. 端到端数据流（时序图，按阶段）
4. 核心数据模型（ER 图 + 关键关联说明）
5. 架构关键决策记录（ADR 表：决策/选择/放弃/原因）

## 及格线

- ☑ 有分层架构图且每层职责清晰
- ☑ 核心内部机制有图 + 关键决策表
- ☑ 有端到端数据流时序图（覆盖多端闭环）
- ☑ 核心数据模型有 ER 图
- ☑ 有 ADR 表且每条含「放弃方案 + 原因」

## 最易挂的坑

- **只有图没有 ADR**：图看得懂但「为什么这么选」缺失，后人无从判断能否改。
- **ADR 不写放弃项**：只记「选了 A」，没写「为何不选 B」，决策不可辩护、易被动摇。
- **数据流不跨端**：只画单端调用链，漏掉家校/多角色闭环，架构理解片面。
