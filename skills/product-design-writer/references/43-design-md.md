# 43 DESIGN.md（AI 自动遵守的设计规范）写作框架

> 源文档：35-设计系统.md / 38-前端页面设计规格.md 的下游产物；通用格式参考 Google Stitch 提出的 DESIGN.md 概念与 VoltAgent/awesome-design-md 收录的实例。
> 成品样例：`references/_example-designmd-chemai.md`（一份真实项目的完整成品 DESIGN.md 精选片段，展示四段结构如何落地）。
> 概念对比：`AGENTS.md` 教 AI 怎么构建项目；`DESIGN.md` 教 AI 项目应该长什么样。

## 回答什么问题

当设计已定稿（35 设计系统 + 38 前端规格），但 UI 由 AI 编码代理（Claude Code / Cursor / Stitch / v0 等）生成时，如何保证「每次生成的界面都符合设计」？答案是把设计压缩成一份放**项目根目录**的纯 Markdown 文件——代理生成任何界面之前自动扫描并读取它。视觉一致性从「每次生成前手工提醒 / 靠人检查」变成「AI 主动遵守全局规范」。

它是给**机器**读的执行规范，与 35 号（给**人**看的设计决策文档）分工明确：

| 文档 | 读者 | 回答的问题 |
|------|------|-----------|
| 35 设计系统 | 设计师 / 评审者 | 色值**为什么**这么定（理念、论证、方案对比） |
| 38 前端规格 | 前端 / 原型 | 每个页面**放什么**组件、什么状态 |
| DESIGN.md | AI 编码代理 | 生成界面时**必须怎么画**（可执行规则） |

## 怎么设计（框架/步骤）

**核心原则一：展开，不发明。** DESIGN.md 是下游产物，遵循分层单向依赖——只把 35 的色值/字体/组件决策、38 的组件模式与状态约定**压缩改写**成机器友好的规则，**禁止出现上游文档里没有的新色值、新字体、新组件**。生成它的正确方式是把 35 + 38 喂给 AI 并要求「提炼，不新增任何决策」；校验方式是逐 token 对照上游文档。

**核心原则二：Prose, not Tokens（规则是配方，色值只是原料）。** 光丢一堆色值，AI 不知道谁用在哪。每个 token 必须带**语义角色 + 使用规则（MUST / NEVER）**：

```markdown
# DESIGN.md 示例（结构示意，色值为样例）
colors:
  primary: "#002147"   # 系统的声音：主按钮 / 侧边栏 / 标题
  accent:  "#0d7377"   # AI 的声音：AI 气泡 / 智能建议
  bg:      "#faf8f5"   # 纸面的声音：页面背景

## Color Rules
主按钮 MUST 用 primary + 白字
NEVER 用 accent 做主按钮 —— 该色专留给 AI 气泡
```

**核心原则三：控制体积。** 文件过大反而稀释遵守率并推高 token 成本（有实测：过大的设计文件使 token 成本 +92%）。目标是「一次读完就能画」：token 表 + 规则清单压缩在一页到数页内，论证过程留在 35 号，不要搬进来。

**推荐结构（Stitch 格式 + 常用扩展，九个 section）：**

| # | Section | 内容 |
|---|---------|------|
| 1 | Visual Theme & Atmosphere | 气质、密度、设计哲学（一段话 + 从 35 搬来的核心隐喻） |
| 2 | Color Palette & Roles | 语义名 + 色值 + 功能角色，附 Color Rules（MUST/NEVER） |
| 3 | Typography Rules | 字体族 + 完整层级表（标题/正文/等宽，各字号字重场景） |
| 4 | Component Stylings | 按钮/卡片/输入/导航的样式与**状态**（默认/悬停/禁用/加载） |
| 5 | Layout Principles | 间距比例、栅格、留白哲学 |
| 6 | Depth & Elevation | 阴影体系、表面层级 |
| 7 | Do's and Don'ts | 设计护栏与反模式（从 38 的三态要求、35 的色值边界提炼） |
| 8 | Responsive Behavior | 断点、触控目标、降级策略 |
| 9 | Agent Prompt Guide | 速查卡：核心色值/字体一览 + 现成的生成提示片段 |

**生成流程（四段处理法）**：把 38 + 35 作为参考输入，按四段产出：

1. **第一段 · 提取设计参数**：从 35 提取全部设计参数填入 YAML 头——色彩全部色值（主色/强调色/背景/语义色/装饰色）、字体全部配置（标题/正文/代码的字体、字号、字重、行高）、间距尺度、圆角尺度。**一条都不能漏；源文档没定义的写 `null`，并编入第四段缺口表**——不猜、不补造。
2. **第二段 · 抽象组件模式**：扫描 38 全部页面，把**跨页面重复出现**的界面组件抽象为可复用组件模式（如对话气泡、状态徽章＝基础类＋颜色修饰类、标题栏、底部导航栏、搜索框、分页控件、弹窗遮罩），每个模式写清 CSS 属性与使用条件。
3. **第三段 · 翻译约束规则**：把 35 的设计理念翻译成 AI 可严格执行的约束——每条用 MUST / MUST NOT / SHOULD 表达，给正例和反例，具体到 CSS 属性级；至少覆盖按钮、颜色、字体、圆角间距四类。
4. **第四段 · 整体约束与已知缺口**：整体约束（留白策略 / 图标原则 / 阴影规范 / 禁止自行发明新颜色）；**已知缺口诚实列出**（如专业符号渲染不归本文件管、平板端适配未定义、深色模式未支持），每条标注该缺口的默认处理方式。

**两种成品形态（二选一）：**

| 形态 | 适用 | 结构 |
|------|------|------|
| **九 section Stitch 格式** | 上游设计系统较薄、需要覆盖布局/阴影/层次等通用维度 | 见上方九个 section 表 |
| **四段合成格式**（真实项目验证） | 上游有两份成熟文档（设计系统 + 页面规格），且采用「生成流程即文档结构」 | ① 设计参数结构化数据块（YAML，null 挂 gap 编号）→ ② 复用矩阵 + 组件模式条目 → ③ C 编号约束规则表（🔴/🟡 + 出处 + 可机械校验标准）→ ④ 整体约束 + G 编号缺口表（含回填机制）；头部声明合成来源、使用方式、冲突裁决规则（「参数冲突时以第一段数据块为准」） |

两种形态共用的**数据块头部元规则**：声明「唯一事实来源是哪份上游文档」「null 值的含义与去向」「禁止自行发明设计参数」——这三条让 AI 在读到歧义时知道听谁的。

**部署与审校**：产出后按四问审——① 色值有没有漏或错 ② 组件模式有没有漏跨页重复组件 ③ 规则有没有模糊词、缺反例 ④ 缺口表完不完整。审完放**项目根目录**，并在 AI 工具配置里加一句「生成界面代码前先读 DESIGN.md」。

**两层结构：** 文件头放 **YAML Front Matter**（机器可直接解析的 token：色值/字体/间距/圆角），正文放 **Markdown 规则**（叙述 + 使用规则 + 组件模式 + Do's/Don'ts）。Markdown 是 LLM 读得最好的格式，无需任何解析配置。

**适用性判断（先判断再动手）：** 适合从零新建、由 AI 生成 UI 的项目；已有成熟组件库的产品收益有限（组件库本身就是规范）。当前普遍只支持单主题，多主题（亮/暗）需写两份或在 section 2 显式分支。

## 文档结构

```
DESIGN.md（项目根目录）
├── YAML Front Matter：colors / fonts / spacing / radius（机器可读 token）
├── 1 视觉主题与气质（一段话定调 + 品牌隐喻一句）
├── 2 色板与角色（语义名+色值+角色表，附 MUST/NEVER 规则）
├── 3 字体规则（层级表：用途/字体/字号/字重/场景）
├── 4 组件样式（每组件：视觉特征 + 状态变体表）
├── 5 布局原则（间距比例 + 栅格 + 留白）
├── 6 层次与阴影（阴影分级 + 表面层级）
├── 7 Do's and Don'ts（正例/反例清单）
├── 8 响应式行为（断点 + 触控目标 + 折叠策略）
└── 9 Agent 提示指南（速查卡 + 现成提示片段）
```

## 及格线

- ☑ 每个色值/字体都能在 35 号找到出处，每条组件规则都能在 38 号找到出处（零发明）
- ☑ 每个 token 带语义角色，关键用法有 MUST / MUST NOT / SHOULD 规则与正反例，不是裸 token 列表
- ☑ YAML front matter 与正文规则无冲突（同一色值同一语义名）
- ☑ 组件模式覆盖跨页面重复组件；Do's/Don'ts 覆盖三态（加载/空/错误）
- ☑ 缺口表完整：上游未定义项显式标 `null` 并给默认处理方式，没有 AI 自行补造的参数
- ☑ 文件体积可控（数页内读完），论证性内容零搬运
- ☑ 放在项目根目录，且已被 AI 代理实际读取验证过一次生成效果

## 最易挂的坑

- **只给 token 不给规则**：贴了一堆色值没有 MUST/NEVER，AI 随机取用，一致性照样崩——原料不等于配方。
- **把 35 号整篇搬进来**：理念论证、方案对比是给人看的决策记录，AI 不需要；体积膨胀反而降低遵守质量。
- **上游改了它没改**：35/38 变更后 DESIGN.md 不同步，AI 按旧规范生成。把它纳入设计变更的检查清单（改色值 → 同步改 DESIGN.md）。
- **拿它当设计起点**：它是定稿后的下游产物。跳过 35/38 直接写 DESIGN.md = 无上游决策的凭空发明，违反单向依赖。
