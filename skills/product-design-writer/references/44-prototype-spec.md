# 44 原型说明文档写作框架

## 回答什么问题

原型（可交互 HTML / figma / 墨刀稿）做完之后、开发排期之前，如何把它翻译成前端、后端、测试**能直接照着评估和开工**的《原型说明文档》？本文档定义这份交接文档的角色定位、七节模块格式、分模块交付节奏与【待确认】制度，让开发「无需再反复追问产品即可开工」。

> **文档不孤立**：这是第 7 段原型设计的**收尾交付物**（第 ⑤ 步交接）。输入有两份——上游产品资料（市场洞察 / 用户与价值定义 / 验证与商业模式 / 产品设计各段结论）+ 原型本身（截图 / HTML / 页面结构描述）。每个字段、状态、接口必须能在原型上找到对应；资料里没依据的一律标【待确认】，不编造。

## 怎么设计（框架/步骤）

**执行三步（必须按顺序，节奏本身就是方法论）**：

1. **先出清单等确认**：通读产品资料与原型，输出《页面/模块清单》，**停下等干系人确认后再继续**——防止一口气写完才发现模块划分错了方向。
2. **每次只写 1 个模块**：按清单顺序逐模块输出，写完整——不允许省略、不允许用「同上」指代（开发会漏读，测试没法独立对照）。
3. **【待确认】制度**：资料中没有明确依据的内容一律标注【待确认】，每个模块结尾附一行「本模块待确认问题清单」——把产品没想清楚的地方显式暴露，而不是让开发自己猜。

**每个模块的七节格式（严格遵守）**：

| # | 节 | 内容与列定义 |
|---|----|------------|
| 1 | 功能说明 | 页面定位（用户在此页完成什么任务）+ 功能点清单表：`编号 / 功能点 / 描述 / 优先级(P0/P1/P2)` |
| 2 | 页面字段 | `字段名 / 类型 / 必填 / 默认值 / 校验规则` 五列，落到可编码颗粒度 |
| 3 | 状态与流转 | 页面级五态（加载中 / 成功 / 空数据 / 错误 / 无权限）各自的展示与操作；业务对象状态机（如有）：`当前状态 / 触发条件 / 目标状态 / 可操作角色 / 备注` |
| 4 | 接口需求 | **业务级定义，不涉技术实现**：`接口用途 / 触发时机 / 入参(字段·类型·必填)`——说清「要什么数据、什么时候要」，不指定技术栈 |
| 5 | 异常与边界 | 网络异常、超时、重复提交、并发冲突、权限不足的处理方式；边界值：空输入、超长文本、极端数量 |
| 6 | 权限与角色 | 哪些角色可见、可编辑、可审批（引用上游权限模型的角色表） |
| 7 | 验收标准 | 3~5 条「**当…时，应该…**」句式，与 PRD 验收标准呼应 |

**硬性要求**：

1. 这是**业务功能说明文档**：不写代码、不指定技术栈、不设计数据库表结构——技术方案是开发的事。
2. **双向对得上**：每个字段、状态、接口必须能在原型上找到对应元素；原型上有但资料没依据的，标【待确认】而不是顺理成章写进去。
3. 字段表、状态表、接口表一律用 Markdown 表格。

**三层对得上的完整闭环**：设计文档（图纸）→ 原型（沙盘）→ 原型说明文档（施工交底）→ 代码（楼）。41 号的追溯码回答「这个元素对应哪条需求」，44 号的字段/接口表回答「这个元素开发要怎么实现、测试怎么验收」。

## 文档结构

1. 文档头：读者（前端/后端/测试）、输入依据声明（产品资料哪些章节 + 原型版本）、全局【待确认】汇总
2. 页面/模块清单（先行确认用）
3. 逐模块七节正文（每模块以「本模块待确认问题清单」收尾）
4. 附录：全局状态码 / 权限角色速查 / 与 PRD 需求编号的追溯对照

## 及格线

- ☑ 先出模块清单并获确认，再逐模块输出；无「同上」式省略
- ☑ 每模块七节齐全，字段表落到「类型/必填/默认值/校验规则」，状态机落到「触发条件/可操作角色」
- ☑ 接口只写业务级（用途/触发时机/入参），零技术栈泄漏
- ☑ 每个字段、状态、接口能在原型上找到对应；没依据的全部带【待确认】标记
- ☑ 每模块结尾有待确认问题清单；验收标准用「当…时，应该…」句式 3~5 条
- ☑ 与 41 号追溯标注对得上：需求编号 → 原型元素 → 说明文档字段/接口，可双向追溯

## 最易挂的坑

- **一口气写完不确认**：跳过「清单确认」直接逐模块输出，模块划分或颗粒度错了只能整篇返工。
- **用「同上」省略**：看似省字，实际让每个模块不可独立阅读，测试无法按模块对照验收。
- **接口写到技术层**：一写就滑向表结构、SQL、框架选型——越界到开发的领域，且很快过时。
- **把猜测写成事实**：原型上有但资料没依据的细节，悄悄补全而不标【待确认】——开发按猜测实现，返工成本最高的一种错。
