# 示范样例：[示例项目A]— 一份完整的产品设计文档长什么样

> ⚠️ **本文件是「示范参考」，不是「模板」。**
> 它展示的是：第 4 阶段的设计骨架落到一个具体行业（教育类 AI 工具）后的**成品形态**。
> 跨领域写作时，你只需观察「分层怎么落、状态机怎么画、矩阵怎么排、字段怎么给、门禁怎么定」——**行业细节（业务名词、算法、字段、服务商）一律按新领域重新生成，绝不照搬。**

> **⚠️ 第三方权利声明（必读）**
> 本文件是「方法论的呈现示例」，**不是事实陈述，也不是任何特定项目的真实材料**。
> 内容基于第三方培训/学习素材中方法论的应用方式做了**重构与脱敏处理**——所有具体名称
> 均为占位符（`[示例项目A]` / `[某学科]` / `[某地区]` / `[某厂商]` / `[某统一考试]` 等）。
> 不应将占位符替换为真实产品名后当作事实证据。具体权利与免责条款见仓库 [NOTICE](../../../NOTICE)。
**样例背景**：[示例项目A]——面向公立高中[某学科教师]/学生/家长的 AI 辅助教学工具，做「拍照识别 → 批改 → 障碍诊断 → 自适应练习 → 学情报告」的闭环。三个用户端（[角色群]），八个设计层。

以下每个片段只截取「最能体现设计方法论」的部分，不展示全文。

## 片段一：批改管线 —— 每步都要有触发条件/技术/耗时，且必须有状态机

**示范点**：① 端到端管线要拆成可编号的步骤，每步写清「触发条件 → 关键技术 → 耗时预估」，让设计可被排期与压测；② 凡是多步异步流程，必须给状态机，且必须含取消/失败终态。

```
10-Step Pipeline：
1 批量上传 → 2 识别 → 3 主体信息提取 → 4 答案来源选择 → 5 语义批改
→ 6 人工确认 → 7 保存结果 → 8 触发下游诊断 → 9 聚合统计 → 10 报告生成

| 步骤 | 触发条件 | 关键技术 | 耗时(预估) |
|------|----------|----------|-----------|
| 2 识别 | 上传完成自动触发 | 定时轮询 5s | 5-30s/张 |
| 5 语义批改 | 答案来源就绪 | 确定性比对 / 模型语义批改 | 3-15s/张 |
| 6 人工确认 | 批改完成 | 前端结果卡片 + 复核 | 人工决定 |
```

**状态机（示范点：终态不止一个，还要有取消路径）**：

```
[*] → UPLOADED → PREVIEWING →（用户分叉）
                              ├─ 导入资源库
                              └─ 进入批改
                                    → GRADING → CONFIRMING → COMPLETED
                                    （任一步可 → CANCELLED / FAILED）
```

> **「所以呢」**：这条管线的设计红线是「**任何一步失败都不能丢失已上传的文件**」——所以上传会话独立成状态机，与业务结果解耦。

## 片段二：权限设计 —— 先角色表，再资源-动作矩阵

**示范点**：权限不是一张"角色说明表"，而是一张**可直接当校验数据源用的矩阵**（行 = 资源+操作，列 = 角色，单元格 = ✅/❌）。矩阵定完再写"权限规则摘要"，让实现者不必读全文就能对齐。

| 资源 | 操作 | 超管 | 教务 | 组长 | 一线 | 学习者 |
|------|------|:---:|:---:|:---:|:---:|:---:|
| 学校 | create/update/delete | ✅ | ❌ | ❌ | ❌ | ❌ |
| 学校 | read | ✅ | ✅ | ✅ | ✅ | ❌ |
| 班级 | create/update | ✅ | ✅ | ❌ | ❌ | ❌ |
| 分析 | read | ✅ | ✅ | ✅ | ✅ | ❌ |
| 核心业务资源 | create/read | ✅ | ❌ | ❌ | ✅ | ❌ |
| 自身数据 | read | — | — | — | — | ✅ |

**规则摘要（示范点：把矩阵读成人话，逐角色一行）**：
- **组长**：全部资源仅 read，**没有任何写操作**（这是刻意的设计：评审者不该是执行者）。
- **一线**：组织类资源只读，**核心业务资源有写权限**——写权限跟着"干活的人"走，而不是跟着职级走。

> **「所以呢」**：矩阵是唯一权威数据源，任何"临时放开一个权限"的改动都必须先改矩阵，再改代码。

## 片段三：策略矩阵 —— 把"判定结果"直接翻译成"干预参数"

**示范点**：上游系统输出一个分类结果，下游系统要把它翻译成**具体参数**（难度偏移、内容选择倾向、题型配比）。这个翻译必须做成**覆盖全组合的矩阵**，并标注每个格子的版本状态（已启用 / 规划中），而不是留在口头约定里。

| 障碍类型 | 难度策略 | 内容选择策略 | 题型策略 | 干预原理（为什么这样配） |
|----------|---------|-------------|---------|----------------------|
| **概念类** | 降低难度，聚焦基础 | 优先基础知识点 | 增加辨析型与基础填空，减少综合计算 | 未建立概念体系，需先降低认知负荷 |
| **审题型** | 保持目标区间难度 | 混合知识点，不限章节 | 增加含陷阱选项与多条件筛选 | 掌握尚可但易忽略关键条件，需训练细读 |
| **表述类** | 保持目标区间难度 | 侧重需规范输出的知识点 | 增加过程分步计分题 | 理解但表述不规范，需强化规范输出 |

**示范点（版本状态显式标注）**：矩阵里每个格子标 `v1.0 启用` 或 `规划中`——设计规范一次写全，实现分阶段交付；避免"设计没想全、实现各写各的"。

> **「所以呢」**：判定结果的**唯一用途**是选参数。如果某个分类项在矩阵里找不到对应策略，说明分类模型与干预策略脱节，要先补矩阵再上线。

## 片段四：评测体系 —— 分层 + 双轨 + 门禁语义

**示范点**：质量体系要按"评估对象"分层，每层一个独立机制；再按"成本与耗时"分快慢双轨，并**明确定义各轨道的门禁语义**（什么情况拦合并、什么情况拦发布）。

| 层 | 评估什么 | 机制 | 轨道 |
|:--:|---------|------|:--:|
| L0 | 工具自身正确性 | 确定性断言 | 快 |
| L1 | 行为轨迹（用哪个工具、参数、顺序） | 黄金场景 + 断言 | 快 |
| L2 | 输出与交互质量 | 模型判官 + 多族 rubric | 慢 |
| L3 | 安全护栏（注入/越权/逃逸） | 对抗语料 + 断言 | 慢 |
| L4 | 性能预算（延迟、token、循环数） | 阈值断言（先软告警） | 快 |
| L5 | 稳定性回归（修过的 bug 回来了吗） | 快照对比 + 回归集 | 快 |
| L6 | 端到端任务 | 场景剧本 + 成功判定 | 慢 |

**门禁语义（示范点：不同轨道用不同门禁规则）**：

| 轨道 | 规则 | 为什么 |
|------|------|--------|
| 快跑层 | **100% 必须绿**，任一确定性失败即阻止合并 | 确定性断言没有噪声，挂了就是真挂了 |
| 慢跑层 | **严重错误一票否决**；分数只做趋势 | 判官分数有固有波动，用分数线拦发布会误伤 |

> **「所以呢」**：评测不是为了出一份报告，是为了回答三个问题——**能不能发（门禁）、变好还是变差（趋势）、下一步做什么（评估先行驱动迭代）**。

## 片段五：数据模型 —— ER 总览 + 数据链叙事 + 隔离设计

**示范点**：数据模型文档不是把表列出来就完事。要先给 **ER 总览**（"系统里有哪些东西、它们怎么关联"），再用「**N 条核心数据链**」把实体串成业务叙事，最后必须交代**数据隔离**（多租户/多组织下谁能看到谁）。

```
四条核心数据链（示范点：把图读成人话）：
组织链：组织 → 层级 → 单元 → 个体    ← 系统的骨骼，所有查询沿此链向下展开，保证跨组织不可见
业务链：评估 → 条目 → 个体作答      ← 支撑诊断、分析、推荐的全部数据需求
关联链：外部角色 ← 绑定关系 → 个体  ← 决定外部角色能看到什么、收什么通知
身份链：统一账户 ← 各类角色         ← 角色字段区分身份，一对一关联
```

**字段规格（示范点：每个实体都要落到字段名/类型/必填/含义，不给概念）**：

| 字段 | 类型 | 必填 | 含义与约束 |
|------|------|:---:|-----------|
| `id` | string | ✅ | 主键，业务前缀 + 时间序 |
| `org_id` | string | ✅ | 归属组织，**隔离字段，所有查询强制带此条件** |
| `status` | enum | ✅ | 状态枚举，与状态机一一对应 |

> **「所以呢」**：数据模型定稿的标志不是"表画完了"，而是**每条查询都能回答"我该用哪个隔离字段"**——隔离设计漏一个字段，前面所有权限矩阵都白做。

## 把样例换成新领域的「动作清单」

拿到新领域（医疗 / 金融 / 硬件 / 企业内部系统 / 消费 App）资料后，参照本样例的落地方式：

1. **先立分层**：照抄"结构 → 流程与权限 → 业务系统 → 智能体 → 数据与分析 → 支撑 → 技术基础 → 前端整合与验证"的递进顺序，**每层只做该层能做的决策**，后层引用前层。
2. **再写结构层**：把新领域的角色清单翻译成页面树 + 导航机制 + 子角色菜单差异矩阵（不要急着写功能）。
3. **流程与权限**：核心流程用流程图逐个画；权限先列角色表，再列「资源-动作」矩阵，最后把矩阵读成"逐角色一行"的规则摘要。
4. **业务系统逐个独立成篇**，每篇统一走这条骨架：
   `设计目标 → 管线/状态机 → 算法与参数 → 数据流 → 接口 → 边界条件与错误处理 → 设计决策（候选→维度→决策→否决原因）→ 不在范围内`
5. **凡"AI 判定"必配**：置信度分级 + 低置信转人工 + 人工覆盖可回写。
6. **凡"生成内容"必配**：确定性校验做硬红线（100% 零错误）+ 规则库软告警 + 独立的多维度审核，**不依赖同一模型自检**。
7. **技术基础**：数据模型给 ER + 数据链 + 隔离设计；接口给端点矩阵 + 关键接口详述 + 错误码 + 限流；选型给候选与否决原因并落 ADR。
8. **收口**：前端页面集中规格 + 流式协议 + 原型验证（方案→评审→原型→需求标注）+ 系统架构图与关键决策记录。

**一句话**：分层不变、状态机不变、矩阵不变、字段与协议的要求不变——**业务名词、算法、数据、供应商全换**。
