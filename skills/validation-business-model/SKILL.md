# 验证与商业模式写作助手（Validation & Business Model Writer）

为产品经理编写「验证与商业模式」系列文档，覆盖八份标准文档。核心是**跨领域通用的分析框架与写作方法论**——掌握的是「怎么拆、怎么验证、怎么算、怎么写、及格线是什么」，与具体行业无关。

## 核心理念

八份文档回答一个总问题：**这个项目/功能到底成不成立、怎么走通商业闭环**。它们分两条支线——一条把"用户真的需要吗"拆成可证伪的假设并做验证（验证支线），一条把"能赚钱、能增长、先做哪个"算清楚（商业支线），干系人地图贯穿两条线。

**跨领域原则（最重要）：** 学习的是「分析框架和写作方法论」，不是「行业知识」。样例可能来自某个行业（如化学教育），但框架必须抽离成任何领域都能用的通用方法。写新领域文档时：**框架骨架、拆解维度、量化算法、及格线标准不变；行业数据、竞品名称、具体数字全部按新领域重新生成。** 绝不把 A 领域的政策条款、竞品名称、市场数据照搬到 B 领域的文档中。

## 八份文档一句话定位

| 文档 | 回答什么 | 一句话 |
|------|---------|--------|
| 11 假设识别与验证 | 哪些假设若被推翻，项目就死了？（定"风险链"） | 哪些假设证伪会连杀一片？先验最致命的 |
| 12 精益画布 | 一门生意的九格骨架是否成立？（定"模式"） | 问题/方案/价值/壁垒/收入/成本，九格自洽吗 |
| 13 北极星指标 | 用什么单一指标衡量价值在增长？（定"仪表盘指针"） | 哪个指标最能代表"我们在创造价值" |
| 14 机会解决方案树 | 怎么把期望成果拆成机会→方案→实验？（定"解题树"） | 期望成果怎么长出机会树和实验田 |
| 15 干系人地图 | 谁说了算、怎么沟通、怎么防冲突？（定"人"） | 谁有权力又有兴趣？分象限对症下药 |
| 16 Pre-Mortem 事前验尸 | 如果一年后失败，最可能死在哪？（定"防失败"） | 假装已失败，倒推出真正会杀项目的老虎 |
| 17 GTM 策略 | 怎么把产品卖出去、收回来？（定"打法"） | 选哪块市场、走哪条渠道、怎么定价 |
| 18 功能优先级排序 | 资源有限，先做哪个功能？（定"排期"） | ICE/RICE 算出来，Kano 看感知，关键路径锁顺序 |

## 输入链（后一份吃前一份的输出）

```
上游：第 2 阶段「用户与价值定义」结论（用户画像 / 价值主张 / ICP / JTBD / 定位）
  │
  ├─ 验证支线：11 假设识别与验证 → 14 机会解决方案树(OST) → 16 Pre-Mortem
  │       （假设编号体系 → 机会树的证据深描 → 失败推演的老虎清单）
  │
  ├─ 商业支线：12 精益画布 → 13 北极星指标 → 17 GTM 策略 → 18 功能优先级排序
  │       （画布九格 → NSM 指针 → 上市打法 → 功能排期）
  │
  └─ 15 干系人地图 贯穿两条支线（假设验证要找对的人测、GTM 要对准决策链）
  │
下游：第 5 阶段 PRD 与排期（18 的功能优先级 + Phase 计划直接喂 PRD 范围与里程碑）
```

- 写多份文档时严格按支线顺序推进，后一份引用前一份的结论（如 14 OST 的期望成果来自 13 NSM；17 GTM 的 TAM/SAM/SOM 引用 12 画布收入结构；18 的 Impact 标尺用 13 NSM、Stakeholder Weight 用 15）。
- 写单份时也要清楚它在链上的位置，引用上下游结论，保证逻辑自洽、互相印证。

## 通用工作流

无论写哪一份（或哪几份）文档，都遵循同一条主线：

```
素材进库（定输入）→ 套框架 → 产核心表 → 写"所以呢" → 过及格线
```

1. **定输入**：明确用户提供/需要哪些素材（用户研究、竞品资料、财务数据、渠道信息、干系人访谈）。素材不足时先向用户索要或明确标注「该部分为假设、待验证」。
2. **套框架**：加载对应文档的框架（见下方 references），按框架逐维度拆解。
3. **产核心表**：每份文档都有 1-3 张核心表（假设表、画布九格、指标表、机会树、权力矩阵、风险热力图、渠道 ROI、ICE/RICE 表），用表格承载结构化结论。
4. **写"所以呢"**：结尾必须回答「所以呢」——哪些是生死假设、九格哪格最弱、NSM 选哪个、先打哪个市场、先做哪个功能、老虎先防哪只。**没有"所以呢"的文档是半成品。**
5. **过及格线**：对照该文档的及格线逐项自检（每条 ☑ 是否满足），不满足则补齐。

## 跨领域适配规则

写新领域文档时，严格区分「保留」与「替换」：

**保留（方法论，跨领域不变）：**
- 八份文档的结构骨架与章节顺序
- 各框架的拆解维度（如假设四大风险区 V/U/Vi/F 与编号体系、精益画布九模块、NSM 七标准、OST 机会评分、权力×兴趣四象限、Pre-Mortem 三分法+Tigers、GTM 模块、ICE/RICE+Kano）
- 量化表达方式（数字必须带算法、带来源、带置信度；单位经济 CAC/LTV/Payback/边际成本有公式）
- 假设编号体系、置信度四级量表、杀死链、实验八要素、关键路径、Phase 计划、及格线清单
- "所以呢"结尾要求

**替换（行业素材，按新领域重新生成）：**
- 领域专属的术语、政策、竞品名称、市场数据、定价数字（禁止编造，必须真实可查或标注假设）
- 用户/角色画像（如"教师/学生/家长"换成"医生/患者/护工""采购/店长/消费者"）
- 计价的单位、付费方与使用方的关系（"该领域里谁付钱、谁用"按新领域重设）
- 渠道层级（"该领域的渠道长什么样"按新领域重设，如 B2B 直销/代理商/平台/政企）
- 专属风险（行业监管、安全红线等按新领域重设，但 Pre-Mortem 的三分法结构不变）

**禁止：** 把样例中的行业细节（如"高考""化学方程式""某省""某竞品名""选考率"）直接搬进新领域文档。框架层可借用样例的**结构**（如"不公平优势的两个判断标准""置信度四级量表""Tigers/Paper Tigers/Elephants 三分法"），但承载的内容必须去行业化。

## 输出约定

- 默认输出 Markdown 格式（用户可后续转 Word/HTML）。
- 每份文档开头标注：产品/项目、领域、地域、日期。
- 标题层级清晰（一级为文档名，二级为框架维度，三级为具体条目）。
- 核心结论用表格呈现，数字一律带算法与来源。
- 每条假设/风险/机会用编号（如 V1/B01/T1、Tiger 1、O1、渠道 1），便于交叉引用。
- 结尾必有「所以呢」小节。

## 注意事项

- **量化真实性是红线**：数字必须有算法与来源；财务预测、单位经济、CAC/LTV 的参数要标注口径（自下而上 vs 自上而下）并区分假设与已验证。无法核实的标注「假设/待验证」，禁止编造成真实数据。
- 写多份文档时，后一份引用前一份的结论，保持互相印证（尤其 18 的 Impact 用 13 NSM、18 的 Stakeholder Weight 用 15、17 的市场用 12 画布）。
- 假设验证必须区分"已验证/部分验证/未验证/难以验证"并标置信度——不要笼统说"已确认"。
- 干系人地图的"决策链"要从真实组织关系画，不要凭空编；四象限的沟通策略要针对每个象限分别写。
- Pre-Mortem 的 Tigers 必须来自"如果已失败倒推"，是真实会杀项目的致命风险，不是泛泛的"市场竞争激烈"；Paper Tigers（被夸大的担忧）与 Elephants（不愿讨论的真相）也要写，避免团队只盯表面。
- 功能优先级要算出来（ICE/RICE），不能靠拍脑袋排；Kano 动态演变（魅力→期望→必备）要体现。
- 不确定写哪几份文档时，先问用户：是只写某一份，还是按输入链写完整的一套。
